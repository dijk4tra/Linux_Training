Linux C网络编程学习笔记 —— 从同步阻塞到I/O多路复用并发服务器

本项目记录了基于C语言的Linux TCP网络编程学习全过程。
代码一共经历了五个版本的迭代，通过不断发现问题、解决问题，一步步从最基础的“单次同步阻塞通信”演进为了“真正的I/O多路复用并发服务器”。

以下是各版本代码的特性说明与架构演进：

================================================================================

Version 01：基础的单次同步阻塞通信 (01_server.c / 01_client.c)

================================================================================
【特性标签】同步、阻塞、一问一答、单次通信

实现功能：
实现了最基础的TCP三次握手连接（socket -> bind -> listen -> accept/connect），以及基础的数据收发（recv / send）。

架构缺陷：

严格的“一问一答”死板模式。代码是同步阻塞的，必须等待一方先发数据，另一方才能收到，如果顺序乱了就会卡死在 recv。

只能服务一个客户端，且只能通信一次，通信完毕后程序进入死循环或结束。

改进动机：
为了打破这种“必须你发一句，我才能回一句”的设定，实现自由收发，引入了 V2 的 I/O多路复用技术。

================================================================================

Version 02：引入 select 实现双向随机通信 (02_server.c / 02_client.c)

================================================================================
【特性标签】I/O多路复用、打破固定顺序、严重Bug(死循环)

实现功能：
通过引入 select 函数，同时监听标准输入（键盘 STDIN_FILENO）和网络套接字（conn_fd / client_fd）。服务器和客户端都可以随时敲击键盘发送数据，真正实现了自由的双向聊天。

架构缺陷（重大Bug）：
当任何一端断开连接（如 Ctrl+C）时，底层 TCP 会发送 FIN 包。select 会将其视为“读事件就绪”并被立刻唤醒。此时 recv 去读已断开的 Socket 会返回 0。
由于代码中没有对 recv == 0 进行判断，导致 select 和 recv 无限极速循环，引发占用 100% CPU 的“死循环刷屏”问题。

改进动机：
必须处理对端断开（EOF）的情况，防止服务器死循环。

================================================================================

Version 03：处理断开连接与单任务架构暴露 (03_server.c / 03_client.c)

================================================================================
【特性标签】修复死循环、单客户端寿命、阻塞等待

实现功能：
加入了极其关键的 if(0 == cnt) 判断。当检测到客户端断开时，通过 break 跳出循环，完美解决了 V2 的死循环Bug。

架构缺陷（单任务服务器）：
由于 accept() 被放在了 while(1) 循环的外部，服务器在其生命周期内只能取出【一个】连接。
如果客户端A连接并断开，服务器也会随之 break 结束进程；如果客户端A正在通信，客户端B连入，虽然内核完成了三次握手（B在全连接队列中），但因为代码不再执行 accept，B永远无法被服务。

改进动机：
服务器不能因为一个客户端断开就挂掉，而且必须能够接纳新的客户端。因此，需要将“大门（listen_fd）”也交给 select 去监听。

================================================================================

Version 04：监听新连接与串行服务器 (04_server.c / 04_client.c)

================================================================================
【特性标签】双位图保护、事件分发、串行服务

实现功能：

引入了教科书级的 set（持久化位图）与 tmp（临时位图）双位图机制，保护了 select 执行后的位图完整性。

将 listen_fd 纳入 select 的监听范围。当有新客户端完成握手时，listen_fd 变得可读，此时调用 accept 绝不阻塞。

架构缺陷（排队串行机制）：
为了防止唯一的 conn_fd 变量被新连接覆盖，本版采取了“防守策略”：当接待一个客户端后，直接把 listen_fd 从监听位图中剔除（关大门）。直到当前客户端断开，才重新监听 listen_fd（开大门）。
这就像餐厅只有一个服务员，接待1号客人时直接锁门，2号客人只能在门外全连接队列里死等。

改进动机：
服务器变成了排队轮流使用的“串行服务器”，而不是同时服务的“并发服务器”。要实现真正的并发，必须找个容器把所有客人的 conn_fd 都存起来。

================================================================================

Version 05：真正的 I/O 多路复用并发服务器 (05_server.c)

================================================================================
【特性标签】并发服务、FD数组管理、广播功能、资源释放

实现功能：

客户端名册管理：引入了文件描述符数组 arr[1024]，用于动态管理所有已连接的客户端。

大门常开：listen_fd 永远保留在监听位图中，随时接纳成百上千的新客户端连接，并将新的 conn_fd 分配到 arr 的空槽位中。

并发收发：遍历 arr 数组处理数据。无论是哪个客户端发来消息，select 都能精准察觉并处理。

群发广播：巧妙利用数组遍历，当服务器在终端输入数据时，会循环对 arr 中所有已连接的客户端执行 send，实现了群发广播功能。

重要修正：

将监听键盘输入的 FD_SET(STDIN_FILENO, &set) 移至正确位置，避免了必须等第一个客户端连入才能敲键盘的逻辑错误。

客户端断开时，严谨地执行了三步曲：取消监听(FD_CLR) -> 关闭套接字(close) -> 数组槽位清零(arr[idx] = 0)，防止描述符泄漏和野指针。

终极形态：
至此，一个经典的基于 select 的单线程并发服务器实现完毕。它能在一个线程内，同时且不阻塞地处理上千个客户端的连接和数据收发。

================================================================================

总结与核心知识点

================================================================================

TCP三次握手与Accept Queue：connect 触发握手，内核自动将完成握手的连接放入全连接队列，直到应用层调用 accept 取出。

select 原理：通过监听位图拦截事件。对端正常关闭（发送 FIN 包）属于【读事件就绪】，必须通过 recv 返回值 0 来判断并处理。

保护位图机制：select 会修改传入的 fd_set（传出未触发的位会被清零），因此每次调用前必须用临时变量重新赋值（tmp = set）。

并发之道：突破单一变量的限制，利用数据结构（如数组）存储所有的通信描述符，交给操作系统内核（多路复用器）统一监控。
